# AgentForge 个人助手轻量化改造方案

> 历史草案：EasyChat 名称、事件记忆和完整自进化范围已在 `2026-11-03-easychat-design.md` 更新；存在冲突时以新讨论稿为准。本文保留作为初次调研记录。

日期：2026-11-03  
状态：方案草案，可据此分阶段实施；本轮未修改业务代码。

## 1. 目标和范围

从当前 AgentForge 派生个人助手项目，保留 Hermes 智能体、微信接入、多端扩展、技能和 MCP 工具调用；彻底移除内置知识库、RAG、GraphRAG 及其评测链路；简化记忆，业务数据库改为 SQLite。

个人助手面向 2 核 2G 服务器。助手进程常态内存低于 1GB 是设计及实测目标，并非当前代码已达到的结论。WeKnora 可以同机或异机部署，本方案不限定位置；通过可配置 MCP 地址连接即可。同机时，WeKnora 的进程和数据库占用需要另计，不能据此推导整机一定足够。

首版默认：个人自用、一个主账号，保留渠道身份绑定的数据结构；沿用已有微信 iLink 接入和 Web 管理界面；不自动迁移历史知识库和复杂记忆。上述默认值可以在实施前调整，不影响先做源码解耦。

## 2. 当前代码结论

以下以工作区源码为准。`CLAUDE.md` 引用的 `docs/项目文档.md` 当前不存在，不能作为最新架构依据。

| 当前位置 | 已确认情况 | 改造含义 |
|---|---|---|
| `main.py` | 启动初始化基础设施、复杂记忆、outbox/reconciler、知识库和评测维护任务 | 需要重写启动装配，不能只删除目录 |
| `backend/agents/prompts.py` | 强制每个问题先调用 `knowledge_search`；描述现有长期记忆 | 改为按需调用可用工具，移除不存在的能力承诺 |
| `backend/tools/tools_decorator.py` | 注册 `knowledge_search`；检索及引用格式化访问本地 KB 表 | 删除本地检索工具及引用查询，不留隐式回退 |
| `backend/hermes_adapter.py` | `skip_memory=True`，手动挂载 `AgentForgeMemoryProvider`；两处缓存上限为 100 | 显式替换记忆提供器、缩小缓存，保留会话恢复 |
| `backend/db/__init__.py` | 数据库工厂仅支持 MySQL | 新建 SQLite 业务存储实现 |
| `backend/db/schema.py` | 对上层提供类似 SQLite 的接口，底层仍是 MySQL，初始化读取 MySQL SQL 文件 | 接口形似 SQLite 不代表能直接切换驱动 |
| `backend/service/platform_gateway.py` | 已有 `ChannelAdapter`，契约只有 start/stop/is_running | 保留生命周期，补统一消息和回复契约 |
| `backend/controller/wechat/*` | 已支持消息、图片、附件和 Hermes；直接引用 MySQL，去重主要在内存 | 接入逻辑可复用，存储与运行入口需要拆开 |
| `backend/controller/wechat/hermes.py` | 微信直接取模型配置、构造提示词、调用 runtime，再借用 Web persistence 落库 | 抽取统一助手服务，渠道不再依赖 Web 控制器 |
| `backend/hermes/hermes_state.py` | Hermes 已有 SQLite 会话库 | 首版保留，避免重写引擎内部会话存储 |
| `backend/hermes/tools/mcp_tool.py` | 已具备远程 HTTP/Streamable HTTP、SSE、认证头和超时配置能力 | 优先复用，实际连通性需要验收 |
| `requirements.txt`、`pyproject.toml` | 默认依赖不一致，混有 RAG、评测、文档和报告组件 | 统一安装入口，重新锁定最小运行依赖 |
| `docker/docker-compose.yml` | 包含 MySQL、Neo4j、Redis、Milvus、etcd、MinIO | 个人助手部署不再携带这些服务 |

限定模式的静态检索已发现：排除内嵌 Hermes 后，20 个 Python 文件引用 MySQL 驱动或连接池，54 个文件引用 RAG/GraphRAG/记忆相关模块。这只是已检索模式的结果，不是完整依赖闭包，实施时必须继续沿调用关系核查。

## 3. 路线比较

| 路线 | 优点 | 代价 | 结论 |
|---|---|---|---|
| 在派生项目中删除重模块，保留 Hermes，收拢存储和渠道边界 | 复用微信、技能、工具、会话能力，能真正减依赖 | 需处理跨层调用及直接 SQL | **推荐** |
| 继续保留完整代码，仅用开关关闭功能 | 短期改动少 | import、副作用、依赖及维护负担仍在，容易误启 | 可用于实施过渡，不作为最终结构 |
| 新写一个极简助手服务 | 结构可从头简化 | 重做现有微信、多模态、工具、会话及错误处理 | 首版不选 |

派生项目首版只支持 SQLite，不维持 MySQL/SQLite 双引擎兼容，也不引入可切换存储插件平台。

## 4. 目标架构与边界

```text
微信 iLink        Web 聊天/SSE        后续飞书/企微等
    \                 |                  /
     渠道适配器：接收、协议解析、身份信息、消息投递
                         |
                AssistantService
       身份绑定 → 会话路由 → 幂等/排队 → 执行与持久化
                         |
                  Hermes Runtime
                  /      |       \
          轻量记忆    技能/工具    MCP Client
              |                     |
      SQLite app.db          WeKnora / 其他 MCP

Hermes SessionDB → SQLite state.db（引擎内部历史）
```

依赖方向：渠道调用助手服务，助手服务调用运行时、存储和工具接口。核心代码不导入微信控制器、KB 服务或图数据库客户端；渠道也不导入 Web 聊天控制器。保留现有模块中稳定的实现，按边界逐步搬迁，不一次性重排整个项目。

建议新增 `backend/service/assistant_service.py`，对外提供统一运行与取消入口。运行结果通过事件返回，Web 转成 SSE，微信累积最终回答并分块发送。模型选择、提示词、记忆、权限、运行锁和落库只执行一遍。

本次不重写 Hermes 内核；已有上下文压缩、工具结果限制、任务证据等能力按依赖核对后保留。长期聊天上下文和长期记忆是两件事，不随删除复杂记忆一起删除会话恢复。

## 5. 知识库/RAG 的完整移除范围

### 5.1 在派生项目中移除

- `backend/rag/`、`backend/graphrag/`、`backend/service/kb/`。
- `kb_controller.py`、`kb_eval_controller.py`、`graphrag_controller.py` 及其路由装配。
- `knowledge_base_mapper.py`、`kg_candidate_mapper.py`、`graph_change_log_mapper.py` 及 KB/KG 专用表和迁移。
- `backend/service/kg/`、`backend/service/graph/` 中仅供本地知识图谱服务的实现；共享实现先查引用再决定。
- `knowledge_search`、本地 KB/图谱工具、文档切片、embedding、rerank、语义检索缓存、本地引用映射与检索统计。
- RAG/KB 专用评测、样本、基准脚本、后台建议生成、管理报表及其默认测试装配。
- Milvus、Neo4j、向量库及相关基础设施探测、配置、健康检查、启动横幅。

不是简单把路由藏起来：默认安装、import、启动、普通聊天、定时执行均不再触达这些模块或旧数据表。

### 5.2 联动清理

- `main.py` 删除 RAG、知识库、图谱及其评测初始化和维护任务。
- 提示词删除“任何问题先查知识库”“禁止不检索直接回答”等规则，按实际挂载工具生成能力说明。
- 工具注册、预置技能、toolset 权限、Hook、会话回放、Trace 标签、引用格式化同步去掉本地 KB 假设。
- 清理委派上下文 `backend/service/delegation/context_enrichment.py` 对旧记忆上下文变量的引用。
- 删除前端 Knowledge/KnowledgeEval/KnowledgeBaseManager 及对应 API、路由、菜单和权限种子。
- 清理 Docker、环境变量样例、启动脚本、文档、依赖锁文件及测试夹具中的旧组件要求。
- 普通聊天附件继续保留；附件解析与“建立知识库索引”拆开。PDF/Office 解析若保留，作为可选能力并设置大小限制。

论文复现、证据图谱、Text-to-SQL、数据库语义索引、企业数据层不属于个人助手首版默认能力。建议从默认工具注册、启动和安装依赖中拿掉，独立保存到原项目；具体删除共享辅助代码前检查引用，避免误伤普通文件处理和工具执行。

## 6. WeKnora MCP 接入

助手只承担 MCP 客户端职责，不复制知识库权限模型、文档索引或检索流水线。文件管理、入库、索引和检索维护留在 WeKnora；首版不在助手前端重建知识库管理界面。

优先复用 Hermes 现有 MCP 客户端。增加薄配置层，将服务器配置映射到 Hermes；不再写一套 MCP 协议栈。工具按远端发现结果注册，并应用允许列表，首版仅开放知识查询和阅读类工具。

按需检索：用户询问个人文档或明确要求查资料时调用；闲聊和普通任务不强制检索。检索返回的来源信息原样保留必要字段，不再访问本地 `kb_documents`/`kb_chunks` 补引用。微信转为可读文本，Web 可展示来源链接。

连接失败、超时和认证失效应返回明确的工具错误，普通聊天仍可使用；不能把失败伪装成“知识库无结果”，也不能在失败后偷偷回退旧 RAG。健康检查分为核心服务存活与外部 MCP 能力状态，外部服务离线不触发整个助手反复重启。配置连接及调用超时、有限重试、返回内容上限和日志脱敏；连接重建后刷新完整工具目录。

截至调研时，官方说明支持内置 Streamable HTTP 端点 `/mcp/<endpoint_id>`，使用端点令牌，旧 Python MCP Server 已弃用。最终接入必须以用户实际部署版本的能力为准，不照搬最新主分支工具名称。参考：[官方 MCP 文档](https://github.com/Tencent/WeKnora/blob/main/website-docs/03-features/08-mcp.md)、[旧服务弃用说明](https://github.com/Tencent/WeKnora/blob/main/mcp-server/README.md)。

远端令牌的权限范围决定其可读取的数据，不能仅依赖助手提示词限制。若未来扩展多用户，按绑定身份选择对应凭证或受限端点，不共用一个有全部知识库权限的令牌。

## 7. 轻量记忆

### 7.1 保留三类简单状态

| 状态 | 保存位置 | 使用方式 |
|---|---|---|
| 当前会话消息和工具历史 | Hermes `state.db` | 复用引擎恢复、上下文预算和压缩 |
| 用户偏好/长期事实 | `app.db` 的 `memories` | 按用户隔离、按需读取，可查看/修改/删除 |
| 会话摘要 | `app.db` 的 `session_summaries` | 超过上下文阈值时更新，辅助长会话，不全量注入历史 |

长期事实首版以显式“记住/忘记”指令或明确的记忆工具调用写入；普通对话不运行后台全量事实抽取。相同用户下采用稳定键覆盖或规范化文本去重，不做向量去重、矛盾裁判、自动晋升或图谱建模。自动工具写入仅用于明确表达的偏好或事实，用户可撤销。

建议实现 `SimpleMemoryProvider`，只对接当前 Hermes `MemoryProvider` 所需接口。长期事实放进有限大小的提示词块，初始上限可设 2,000 tokens；超过预算按明确的优先级、更新时间裁剪，完整内容仍可通过记忆工具读取。首版不用 FTS、embedding 或语义召回；数据量确实增长后再考虑 SQLite FTS5。

摘要仅为压缩结果，不是事实库。优先复用 Hermes 已有压缩产物，避免每轮额外调用模型；若当前引擎无法直接复用，则在压缩节点生成一次摘要。摘要失败不影响原始历史和本轮结果。

### 7.2 删除旧系统及桥接

移除旧 `backend/memory/` 实现、`backend/service/memory/`、`memory_mapper.py`、复杂记忆审计和评测，取消 episodic/semantic 分层、自动晋升、TTL 淘汰流水线、Neo4j/Milvus 镜像、outbox worker 和 reconciler。

同步修改 `hermes_adapter.py` 中配置播种、提供器注册、旧记忆引用 ContextVar、运行结果引用字段和缓存逻辑；不能仅删除 provider 文件。前端保留简单记忆 CRUD 页面，移除 MemoryDashboard 和实验/评测面板。所有记忆操作从运行上下文取得可信 `owner_id`，不允许工具参数指定其他用户。

不把聊天原文或所有长期记忆默认同步给 WeKnora；个人记忆与外部文档知识库分开管理。

## 8. SQLite 数据层

### 8.1 存储选择

首版使用标准库 `sqlite3` 和明确的 repository 方法，避免为了换数据库引入新的 ORM。数据库操作短小、带事务；异步入口通过受控线程执行同步查询，不在事件循环内执行可能阻塞的数据库工作。

业务库用 `data/app.db`；Hermes 保留 `data/hermes/state.db`。两者都是 SQLite，分库不增加数据库服务进程，也不急于侵入 Hermes 实现。

`state.db` 是模型恢复所需原始消息和工具历史的权威来源；`app.db` 的会话/对话记录用于业务列表、渠道、状态、关联与界面展示。用 `session_id`、`run_id` 关联，避免额外保存第三套完整历史。跨库无法做普通单库原子事务：重启时将未完成 run 标记为 interrupted，并检查引擎会话后决定恢复或提示重试；不得仅因业务投影写入失败而再次执行有副作用的工具。

### 8.2 建议最小表域

| 表域 | 主要职责 |
|---|---|
| `users` | 主账号和基础登录；默认关闭公开注册 |
| `channel_accounts` | 渠道机器人账号、启用状态和凭证引用 |
| `channel_bindings` | 渠道外部身份到内部用户的受控绑定 |
| `sessions` | owner、渠道/账号/外部会话、Hermes 会话 ID 和状态 |
| `conversations`、`attachments` | 业务对话展示与附件元信息，复用现有字段时做精简 |
| `runs` | 执行状态、来源消息、幂等键、错误和开始/结束时间 |
| `channel_events`、`deliveries` | 持久去重、接收状态、回复分块及发送重试 |
| `memories`、`session_summaries` | 简单长期事实及摘要 |
| `model_configs`、`app_settings` | 模型与应用配置；MCP 地址及凭证引用可纳入设置 |
| `scheduled_jobs` | 若保留提醒，存触发时间、会话及投递目标 |
| `schema_migrations` | 只管理个人助手所需的版本化迁移 |

这不是照搬旧库全部表。简化企业 RBAC、类别、数据层和排行榜；保留主账号鉴权、资源归属检查和工具权限。密钥通过环境变量或受保护的配置管理，不以明文出现在日志、接口返回或仓库。

### 8.3 SQL 迁移和并发原则

- 将控制器/服务里的直接 SQL 收拢到对应 repository；优先会话、身份绑定、模型配置、微信配置、定时任务、最小 Trace。
- 审计 `%s`/`?` 占位符、MySQL DDL、自增类型、JSON、日期函数、UPSERT、索引和排序行为；逐条重写必要 SQL，不用字符串全局替换模拟 MySQL。
- 新建 SQLite schema 和迁移，不执行 `sql/agentforge_schema.sql`，不创建任何 KB/图谱/旧记忆表。
- 每个连接启用外键，配置 busy timeout；使用受支持且已修复已知问题的 SQLite 运行时，按运行时能力启用 WAL，复用并核对 Hermes 已有兼容检查。
- 每个工作线程按操作取得连接，不让多个线程无锁共享一个连接。单应用进程内串行化业务写入，事务中不执行 LLM、网络调用或等待工具。
- 短事务、有限忙重试，避免逐 token 写库。接收和完成状态持久化，流式内容按批或完成后写入。
- WAL 改善读写并发，但不提供无限多写者；SQLite 数据卷放本机持久磁盘。参考：[SQLite WAL](https://www.sqlite.org/wal.html)。
- 通过在线备份接口备份活动数据库，分别备份两库及配置/附件，记录共同备份批次；必要时短暂停止接收新 run 得到协调快照。进行恢复演练。参考：[SQLite Backup API](https://www.sqlite.org/backup.html)。

## 9. 微信和多端接入

保留现有 iLink 扫码、凭证保存、长轮询、文本/图片/文件处理、分块回复、重连、会话切换。既然当前项目已有 iLink，首版不引入新的微信协议依赖。

在现有网关上增加两个小契约：

- 入站消息：`channel`、`account_id`、`external_user_id`、`external_chat_id`、`external_message_id`、文本、附件引用、时间和协议元信息。
- 出站回复：目标账号/会话、内部 run、回复文本/附件、分块序号和发送状态。

账号、外部用户和会话必须组合定位，不能仅用渠道名或昵称作为身份。跨端默认共享同一主账号的长期偏好，聊天线程各自独立；Web 可以查看自己的微信历史。若以后需要接着另一端的同一话题聊，提供明确会话选择，不默认把所有渠道消息混进一个上下文。

消息处理顺序：受控绑定校验 → 接收事件持久化/去重 → 会话路由 → 有界排队 → 统一助手执行 → 保存结果 → 创建投递记录 → 渠道发送。相同会话串行，不同会话受全局并发上限控制；模型运行不持有 SQLite 事务。

去重键至少包含渠道、机器人账号和外部消息 ID。没有平台消息 ID 时优先使用可用的事件序号/游标等稳定信息；确实只能使用短时指纹时，应明确其近似性并设置窄窗口，不能把用户连续发送相同文本永久判成重复。

发送失败只重试已生成结果，不重新执行智能体。重启后恢复 pending 投递；若发送接口没有幂等键，发送成功但本地确认失败仍可能重复，记录这种不确定状态，不承诺端到端 exactly-once。平台回复窗口和消息长度按现有协议实际能力处理。

微信目前无终端审批界面，继续保留现有限制。MCP 和自定义工具也应用同一权限策略，防止换个工具入口绕过限制。图片/附件设置下载大小、超时和处理上限，避免微信媒体消息拉高内存。

提醒/定时任务对个人助手价值较高，建议保留一个简单调度器和渠道投递能力；已有 `backend/service/cron/` 可复用，任务存储迁移 SQLite。复杂报表、邮件运营及管理统计不进入默认版本。

## 10. 部署与资源控制

默认部署只启动一个助手应用进程，单 Uvicorn worker，微信监听、调度器和运行注册表均由同一进程管理，避免重复消费。Web 静态资源在构建阶段生成，由应用或已有反向代理提供；线上不运行前端开发服务。

起始配置建议：全局并发 run 为 1，同会话并发为 1；运行队列有界并给出排队/繁忙状态；Agent 和 Runtime 缓存统一限制为 5～10 个并设闲置回收，确保回收关闭相关资源且不清理活跃运行。委派工具默认关闭，确需开放时共享全局并发预算。附件缓存、SSE ring buffer、HTTP 连接和日志都有上限。

业务缓存使用小容量进程内 TTL/LRU，不需要 Redis。影响正确性的接收去重、投递和任务状态落 SQLite；不能因为去 Redis 就把这些状态全部放进内存。

不在默认进程中启动本地模型、embedding、OCR、浏览器或 Docker 沙箱。若以后需要这些工具，作为显式可选能力或远程服务接入。

内存目标只约束助手进程：常态低于 1GB，目标负载下无 OOM，RSS 不随长时间消息和会话数量持续增长。初版以真实镜像测量启动、空闲、连续对话、长上下文、媒体消息、MCP 大结果和重连峰值；不先给各模块编造精确 MB 预算。同机部署 WeKnora 时单独测量整机余量。

默认保留结构化日志、run 错误、模型调用耗时/token 用量和最小执行记录；去掉重型评测、全量 Trace 明细和多维统计的常驻维护。排障详情按需启用，日志轮转并配置保留期。

## 11. 复制和实施顺序

### 阶段 0：建立安全的派生基线

按用户设想，先复制当前项目作为完整功能的源码基线，再在当前 `E:\PythonCode\AgentForge` 中实施个人助手改造。副本目录和项目新名称在实施前确定；本轮不执行复制。复制源代码时纳入需要保留的未提交修改和未跟踪源码，不只复制 HEAD；当前工作区已有 Hermes、上下文证据、工具执行、Trace 等修改，不能覆盖。

源码副本排除数据库卷、缓存、日志、上传、模型、虚拟环境、`node_modules`、构建产物、真实 `.env` 和密钥。源码副本不等于数据备份：原数据库、上传和必要配置单独备份至受保护位置，不删现有数据卷。改造后的助手使用新的配置和独立数据目录，避免连接旧业务库。记录 Git HEAD、源码差异与未跟踪源码清单，并核验副本后再删除功能；原 Git 历史保留，不自动向远程仓库推送。

### 阶段 1：截断知识库/重基础设施启动链

清理启动装配、强制检索提示词、工具注册和本地引用格式化；从派生项目移除 RAG/GraphRAG/评测模块及前端入口，解除复杂记忆启动依赖。临时禁用旧记忆可作为过渡，但不影响会话历史。

阶段验收：代码不再引用被删除模块；相关服务全部停止时，干净环境可 import 并完成轻量启动装配。不以“捕获异常后跳过”掩盖核心存储尚未迁移的问题；完整聊天验收在阶段 2 完成。

### 阶段 2：SQLite 最小业务闭环

先完成 schema、repository、主账号、模型配置、会话及对话、渠道配置和绑定，再迁移保留的提醒及最小运行记录。移除 MySQL 工厂、驱动、连接池和旧迁移入口；可保留调用方所需的薄接口适配，但不长期保留全套 MySQL 兼容层。

阶段验收：空目录初始化 SQLite、登录、Web 对话、微信绑定/对话、重启后的会话恢复均可用，且没有 MySQL 网络访问。

### 阶段 3：统一助手执行与多端消息契约

将微信和 Web 的模型选择、运行、持久化迁入 AssistantService；实现绑定、会话路由、持久去重、运行队列及投递状态。保留两端各自的协议显示逻辑。

阶段验收：相同主账号跨端共享身份但线程独立；重复消息不重复执行；投递失败不会重跑工具；会话并发顺序稳定。

### 阶段 4：轻量记忆与远程 MCP

挂载 SimpleMemoryProvider，替换旧引用协议；接入真实 WeKnora 端点并验证来源展示。先做能力发现，再确定允许工具和参数，不预设用户部署版本。

阶段验收：记住/读取/修改/忘记跨重启有效，历史对话可恢复，MCP 故障时普通聊天可用。

### 阶段 5：依赖、镜像与资源验收

删除仅用于已移除模块的包；排查 Hermes 延迟导入和插件发现再决定 LangChain 等依赖是否还需保留，不能按包名猜测。同步 pyproject 和安装入口，运行依赖与开发/评测/可选文档工具分离并锁定版本。收敛 Docker、环境变量和前端菜单，构建干净镜像验证。

新 compose 只编排助手及其数据卷；WeKnora 由外部地址配置，用户自行决定同机还是异机。记录内存、并发、延迟、运行时版本和镜像大小，做备份恢复及重启验收。

## 12. 数据迁移和回退

默认个人助手从空业务库起步，不迁移知识库和复杂记忆；原项目源码副本、Git 历史及其 MySQL/其他数据卷保留。需要旧对话时，另做一次性导出导入，明确 ID、owner、Hermes 会话映射，校验计数与抽样内容；不能只迁 Web 展示记录就宣称引擎能继续旧对话。

用户偏好如需保留，先导出待审阅列表，再导入精简记忆，不能把大量 episodic 历史无差别塞入提示词。失败时停止派生实例并恢复基线与备份，不双写原业务库。

## 13. 最终验收清单

- [ ] 干净安装不要求 MySQL/Redis/Neo4j/Milvus/etcd/MinIO，不包含 RAG/图谱/评测运行依赖。
- [ ] 普通聊天、微信和定时任务不会读取 KB/图谱/旧复杂记忆表或强制本地检索。
- [ ] 主账号登录、模型设置、绑定、历史、附件、技能与保留的工具通过 SQLite 完成闭环。
- [ ] 工具原始历史与 Web 展示历史的职责清晰，跨库失败不会重复执行有副作用操作。
- [ ] 微信扫码、重连、会话切换、图片/附件和长回复保持可用；网关状态反映实际监听状态。
- [ ] 未绑定外部身份拒绝使用；按渠道账号隔离去重；主账号资源检查不可绕过。
- [ ] 重启后接收/投递状态可恢复，发送失败只重试投递，同会话串行、队列有界。
- [ ] 简单记忆支持增删改查和重启恢复；摘要及长会话上下文有上限。
- [ ] MCP 真实端点发现/调用/来源可用，断线、超时、401、空结果的处理可区分。
- [ ] 前端无已删除功能的菜单、路由和后台请求，核心设置与简化记忆页面可用。
- [ ] 两个 SQLite 库备份恢复成功，普通负载没有持续锁错误。
- [ ] 单 worker 连续运行及目标消息/媒体负载实测，助手进程达到常态低于 1GB 目标；记录峰值和未覆盖场景。
