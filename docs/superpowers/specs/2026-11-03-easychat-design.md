## 2. 相较上一版，需要改变的设计判断

1. **记忆不能只剩偏好和摘要。** 微信长期聊天还需要可追溯的事件记忆，能回答“上次我担心的那个直播问题是什么”。
2. **自进化目标较完整。** 用户希望自动积累经验、生成/改进技能和脚本；应设计候选、验证、激活、反馈、回滚全链路，而不是只保存几条反思文字。
3. **按已确认范围精简，保留可复用内核。** 技能社区、知识库和论文复现可移除；RBAC、Token 排行榜、个人技能库、微信提醒、执行记录保留，邮件/PDF报告按需启用。Hermes 已有技能管理、后台审查、来源追踪和归档机制，应先审计复用，避免重新造完整框架。
4. **复杂度主要来自存储同步和执行链路，不来自一条排序公式。** SQLite 内计算少量分数并不昂贵，真正需要控制的是多轮模型调用、全量扫描、Agent 副本和无界后台任务。
5. 不限制 WeKnora 同机或异机；助手进程常态低于 1GB 是待实测目标，不将源码大小或文件数量等同于内存占用。

### 3.1 RBAC：保留业务能力，迁移存储

保留用户管理、角色管理、角色权限、用户单独授权和工具集控制；沿用现有角色语义及权限优先级，迁移前记录基准，不因“个人助手”定位退化为单账号开关。平台身份绑定到内部用户，Web、微信、MCP工具、自定义工具、技能和定时任务均使用可信用户上下文进行授权。

SQLite 至少承接 users、roles、role_permissions、user_permissions、permission_defs，以及现有实现中承载工具集配置的字段或表。仅删除已移除功能（本地KB、GraphRAG、论文等）的权限项和默认分配，不保留悬空种子，也不向角色自动追加新能力。

认证、权限判断和资源归属分工保持清晰：角色允许操作某类资源，仍需检查是否拥有目标会话、记忆、技能、报告和提醒。后台进化继承发起用户的能力范围，不能自行改角色、授权、令牌或工具策略。跨用户候选/缓存以用户和权限范围隔离，避免复用错误的凭证或授权结果。

部门不是角色授权的同义词，保留 RBAC 不意味着必须保留本地知识库数据层；部门功能是否简化另行讨论，本轮不删除。

### 3.2 Token 排行榜与统计

已核实当前 `get_ranking()` 从 daily_user_stats 汇总用户Token和API调用次数，按总Token降序展示，路由 `/api/traces/ranking` 使用 `trace.view` 权限。现有统计/排行界面保留并迁移，不将其当成可删的社区排行榜。

业务库保存调用用量和日汇总，统计写入用 SQLite UPSERT 替代 MySQL 语法；以稳定调用ID/完成标识避免重放或重试重复累计。真实发生的独立重试调用仍分别计量；模型调用与工具调用不能混为一条计量口径。日汇总与用量明细在短事务中保持一致，允许从保留明细核对重建。

区分前台聊天、记忆整理和自进化用量，后台调用归属发起用户或明确的系统主体，不能漏计或全部归给管理员。提供输入、输出、缓存等供应商实际返回字段；未知用量留空或显式标为估算，不能把缺失值当成真实零消耗。不同供应商缓存字段按统一适配规则解释，避免将已包含的Token再次累加。

维持已有排行榜查看授权语义；用户能看自己详情与能看全体排行是两种数据范围，前端与接口必须一致，不能因为能看汇总就泄露其他用户提示词和聊天内容。日边界按项目统一时区计算，SQLite中明确索引与(user_id, stat_date)唯一键。小容量进程缓存替代 Redis；详细Trace清理不能顺带删除仍需展示的历史日汇总。

### 3.3 邮件与 PDF：保留、按需运行

保留SMTP发送配置、收件人配置、邮件投递、PDF生成与渠道附件发送，以及提醒选择投递渠道和报告格式的能力；统一迁移到 SQLite，并延续RBAC和资源归属检查。普通聊天不要求配置SMTP，文本提醒不调用PDF渲染器。

邮件和PDF按能力开关、投递目标和格式需求加载；可选渲染依赖可以通过部署依赖组安装，启用前检查完整性，缺失时给出明确的能力不可用状态，不静默丢附件。按需启用不等于删除现有模块或只保留菜单。

新建提醒建议默认微信/文本，用户可指定邮件/PDF；历史任务保留原有渠道和格式，不批量将既有PDF任务改成文本。重型PDF渲染用受控任务/进程，限制并发、时长、输入输出和临时文件；统计整机峰值，不能仅凭懒加载保证不超过内存目标。

生成和投递分成两个状态：报告已生成但邮件发送失败时，重试发送同一产物，不重跑智能体。发送与附件状态可追踪，敏感SMTP配置不暴露给日志、模型上下文和普通用户。自进化回放中以替身模拟邮件/微信发送，不能借验证触发真实外发。

### 不应误删的能力

- 会话 SQLite、上下文压缩、取消、运行队列、SSE与微信回复、附件边界和身份绑定。
- `backend/context/` 中任务状态、原始工具结果和证据索引；它们可帮助验证任务，不能因为有“上下文/搜索”字样就当成知识库 RAG 删除。
- 简单技能文件格式和 `skill_manage`；插件发现按必要模块装配，不直接砍掉整个 Hermes CLI 目录。
- token/耗时/工具结果/用户反馈的最小追踪。自进化需要证据，不能一边删除全部轨迹一边要求验证改进。
- `run_python` 或脚本执行能力不再建议整体删除，但需要摆脱内置 KB/SQL 工具环境，按用途拆开。现有进程内 AST 检查和工具组合不等于任意脚本的可靠隔离环境。

## 5. 对用户图片的判断

### 5.1 结论与取舍

建议实现它的核心能力，但不把整张图直接变成首版规范。图片是一套记忆召回、排序和强度维护机制，**尚不构成技能/脚本自进化闭环**。

| 图片机制 | 建议 | 理由 |
|---|---|---|
| 拆 people/topics/keywords/时间等线索 | 实现简化版 | 适合模糊回忆、人物与话题定位；保留“用户没说清楚”的不确定性 |
| 匹配度与近期性、重要性排序 | 实现 | SQLite 候选集合上计算即可，不需要向量库或图数据库 |
| unfinished / 未完成事项权重 | 有条件保留 | 事实源应是明确待办状态，已完成要更新，不能靠模型一直猜“未完成” |
| affect / 情绪线索 | 作为可选标签 | 可记“那次表达担心”，不生成长期性格/情绪定性，也不默认加大权重 |
| 全表扫描 | 只可作小规模原型 | 正式版先按用户、时间、实体/话题与状态取候选；不每次把全部记忆发给模型 |
| strength 强化、每日整理 | 后续按反馈启用 | 先有来源和质量信号，再决定强化规则；排序用的强度不能代表真实性 |
| 共现关系、association | 首版不做 | 同时被检索不证明有关联，容易把检索偏差变成关系；以后有收益证据再加轻量关联表 |
| 低于阈值从候选集中移除 | 改成分层检索 | 冷记忆默认降权，但明确回忆旧事时仍可检索；除用户删除外不自动物理清除 |

### 5.2 图片中需要先澄清的细节

1. 第⑤步 A/D 均写 hit_log，第⑥步却 D 的当日 k=0。若 k 是检索命中次数，两者不一致；若指实际使用或正反馈次数，就应分别命名。EasyChat 区分 retrieved、used、confirmed、rejected，不让曝光自动变成奖励。
2. 每晚衰减要明确 `Δt` 是距离上次维护，还是距离最后有效使用。如果每天对已衰减 strength 再乘“距最后使用的累计天数”，会重复衰减。可记录 last_decay_at 做增量计算，或者保存基准值、读取时计算，不能混用。
3. 所有人的 `people=[用户]` 都命中，辨识力有限；如果理解线索错了直接剪枝，正确记忆永远进不了候选。保留宽松召回或历史对话检索回退，再做有限候选比较。
4. 近期性在激活值和长期强度维护中都出现，可以作为两个不同目的的参数，但必须用用例校准，不能因为图中有精确小数就认为权重已被验证。
5. 用户纠正要优先更新来源和适用范围。比如“这次不用表格”不应永久覆盖“我通常喜欢表格”；低频旧事实也不应自动变成错误事实。

### 5.3 建议的首版召回链

识别是否需要个人记忆 → 解析时间/人物/话题线索 → SQLite 拉取有限候选 → 相关性优先排序，时间/重要性辅助 → 必要时对少量候选做模型比较 → 注入有限摘要与来源 → 回答并记录实际使用和反馈。

用户当前明确指令优先于偏好；明确询问过去时，事件时间优先于“最近被访问”的时间。记录 event_at 与 recorded_at，后补录的旧事不能当成刚发生。无法定位时给出候选或说明没找到，不用经验规则补造用户经历。

纯关键词可能遗漏同义表达，首版承认这个边界，增加别名/关键词扩展和原始对话回查；有真实漏召回用例后再评估远程 embedding。这个个人记忆检索属于助手必要能力，不等于重建文档知识库和通用 RAG 平台。

## 6. 记忆模型：足够完整，但只用一套轻存储

### 6.1 三种长期记忆、两种运行状态

- **用户事实/偏好**：称呼、输出习惯、常用项目、稳定背景，有范围、来源和更新时间，可固定保留。
- **事件记忆**：用户经历、讨论过的问题、约定、关键决定，保存人物/话题/发生时间/来源消息和状态。
- **经验记忆**：任务中什么方法有效/无效、适用前提、失败原因和证据；属于助手行为知识，不冒充用户事实。
- **当前任务状态**：计划、待办、执行进度，保留现有上下文管理；不是永久记忆。
- **原始聊天和会话摘要**：Hermes state.db 保存完整执行历史，摘要帮助压缩；不是唯一可检索的长期事实源。

SQLite `memories` 可用 kind 区分三种长期记忆，不再设计 episodic→semantic 多库存储晋升。公共字段：owner、kind、content、source_session/message/run、event_at、recorded_at、scope、status、confidence、pinned、supersedes_id、version；实体/话题标签放轻量关联表。记忆修订和反馈保留可撤销记录。

静态 profile 不必全量注入，事件/经验按需召回。记忆与技能清单都有上下文预算，初始上限在实际模型下配置；原始聊天和完整工具输出不直接常驻进程内。

### 6.2 自动写入与纠错

- “记住/忘记/以后都”明确指令即时处理；稳定偏好和重要事件可自动产生候选，普通闲聊不每句都永久入库。
- 用户纠正、任务完成、明确失败和会话阶段结束触发增量提取；同一轮已处理信号不重复入库。
- 原文、模型推断、工具返回、用户确认明确区分。工具说“成功”不等于任务被用户认可；模型自评不等于事实证据。
- 矛盾处理优先作用域/时间与用户纠正，保留旧版本，不再用两条句子里同时出现“喜欢/不喜欢”等简单对立词直接删除。
- “沉底”是默认不注入、可再查的归档状态；主动要求彻底遗忘时，需同时处理摘要、衍生记忆和后续自动提取，避免从旧会话再次生成已删除记忆。物理聊天保留/删除和备份生命周期作为单独用户设置。
- 整理只处理新增/变更，闲置时小批运行；有新消息时前台优先。SQLite 持久化小型任务队列，不额外部署 Redis/Celery。

### 6.3 中文检索

首版必须验收“直播/开播”“那天/上次”等真实中文表达。FTS5 是可选索引，不应将默认 tokenizer 当成中文语义搜索。采用显式标签/别名与分词后的词项索引，并验证运行时能力；trigram 对短于三个字符的查询有限制，短词要有单独召回路径。[SQLite 官方 FTS5 文档](https://www.sqlite.org/fts5.html)

## 7. 自进化：完整闭环，按可验证范围自动执行

目标是优化记忆、经验、技能、脚本和工具使用策略；不训练模型权重。在线聊天、增量学习和可重放实验分成三条调度路径，共享队列、权限与预算。

### 7.1 闭环

任务轨迹/用户反馈 → 发现可复用做法或明确失败 → 形成带证据的经验 → 提出技能/脚本候选 → 格式和静态检查 → 隔离验证/历史样例回放 → 与当前有效版本比较 → 激活或保留候选 → 观察真实结果 → 降级、撤销或继续迭代。

每条经验包含：触发场景、适用前提、建议做法、反例、证据 run/消息、确认程度、适用工具/版本和有效期。一次有效做法可保存为候选经验，但不能自动宣称普适。

### 7.2 自动化边界（用户已确认）

| 对象 | 已确认的范围 |
|---|---|
| 明确偏好、事件、用户纠正 | 自动记忆并允许撤销 |
| 任务经验 | 自动整理和召回，保留证据/反例 |
| 提示词片段、技能说明、工具用法 | 在限定目录生成候选，校验并通过回归后可自动启用 |
| 新脚本/脚本补丁 | 可以自动生成、隔离测试和版本化；仅在预先配置的工具/文件/网络范围内自动使用 |
| 新外部能力、凭证、系统依赖、对外写操作 | 由产品的显式能力设置决定，不通过修改技能描述扩大授权 |
| EasyChat 服务源码、鉴权规则、权限策略、数据库迁移、部署配置 | 首版不允许后台进化直接改生产版本；可形成差异建议，走普通开发验证发布 |

这不是要求每次小改动都问用户。推荐低风险、能验证的更新自动完成，进化记录说明改了什么、依据和回退入口；只有越过已设能力范围时才需用户决定。

### 7.3 脚本验证与副作用

进化脚本在独立工作目录、独立进程和受限身份中运行；限制时间、内存、输出与可见文件，网络默认按允许列表，按需选择更强隔离或远程 runner。独立子进程只是资源边界，不等于完整安全沙箱。业务凭证由工具代理处理，不整包注入生成脚本。

回放可使用工具返回快照、替身或无副作用的测试资源；微信发信、提醒创建、文件写入、外部 MCP 写操作不能为了比较候选而在真实环境重复执行。隔离 runner 暂不可用时可以生成和检查候选，不能把“检查通过”记为“执行验证通过”。

技能发布使用独立候选版本及原子激活指针；保存内容指纹、父版本、产生原因、验证结果、激活时间和回退版本。用户手写/固定的技能不被后台覆盖。仅更新 .usage.json 或执行一次静态扫描，不足以替代版本发布闭环。

### 7.4 预算、触发与降级

不每轮都额外启动完整 Agent。明确纠正、失败后成功、重复操作和任务收尾优先触发；闲置时批量整理。初始并发只允许一个学习/验证任务，共享整机资源预算，前台聊天优先。

提供单任务调用/token/时间预算、每日学习预算、最小间隔和一次性停止开关。未验证、无法判断好坏或超预算时保留原版；新经验可以待确认，不能为了证明“进化”而强制发布。语气更自信和回复更长不是质量改进指标。

## 8. Harness²：是否采用

**建议：借鉴机制，首版不把整套 Harness² 接入在线微信处理；保留后续离线适配选项。** 详细核查见 [调研报告](../../research/2026-11-03-harness2-assessment.md)，固定上游提交 `6868817518876de8fd170c6a8354daca273b6191`。

它优化模型周围的提示词、技能和执行系统，与用户事实/事件记忆不是同一职责。当前执行底座为 Codex/OpenCode，Hermes 需要适配执行、任务、轨迹和产物接口。[执行器接口](https://github.com/google-research/harness2/blob/6868817518876de8fd170c6a8354daca273b6191/harness2/substrate/base.py#L26)

调研确认 k=1 的正常路径包含四次任务执行和三个改进阶段，单候选不调用选择器，开启经验库且采用成功后才追加反思；不能据此换算固定 API 次数。适用于可重放任务，不宜逐条微信消息重复运行。[预算账本](https://github.com/google-research/harness2/blob/6868817518876de8fd170c6a8354daca273b6191/harness2/core/ledger.py#L15)、[调度](https://github.com/google-research/harness2/blob/6868817518876de8fd170c6a8354daca273b6191/harness2/core/schedule.py#L561)

它的基础 Python dependencies 为空，不能据此说框架自身内存大；外部执行器和实验环境另计，EasyChat 未做资源测试。[项目元数据](https://github.com/google-research/harness2/blob/6868817518876de8fd170c6a8354daca273b6191/pyproject.toml#L11)

最终选择池排除 baseline，属于它的实验设定；产品应额外实现“不能证明优于当前版就不启用”。因此直接接入也不能省掉本方案中的发布、回归和回滚。[选择逻辑](https://github.com/google-research/harness2/blob/6868817518876de8fd170c6a8354daca273b6191/harness2/core/selection.py#L93)

最值得借鉴：有来源的经验、有限候选、基于执行证据比较、变更指纹和预算账本。先在现有 Hermes 能力上补齐这些，减少第二套运行框架；以后用脱敏历史任务衡量收益，再决定是否实现 Harness² 适配器。

三条路线比较：

| 路线 | 好处 | 成本 | 建议 |
|---|---|---|---|
| Hermes 既有技能/审查能力 + SQLite 记忆/版本/验证 | 复用最多，符合轻量运行 | 需要收拢并补齐验证和发布 | 首选 |
| 在线维持 Hermes，离线另用 Harness² 做专项优化 | 方法系统，能探索多个候选 | 需执行器/任务适配和隔离回放 | 后续可选 |
| 整套 Harness² 成为每轮在线处理层 | 统一实验流程 | 多次执行、延迟、副作用和模型预算压力 | 当前不选 |

## 9. 方案阶段与验收

当前阶段继续完善方案，不因部分需求已确认就开始功能删除。建议整体方案确认后按四个闭环交付：

1. **轻量底座**：SQLite、删除已确认的KB/RAG与其他冗余业务、统一微信/Web入口、MCP、技能与提醒；保留RBAC、Token排行、邮件/PDF按需能力和最小证据轨迹。
2. **可追溯记忆**：事实/偏好、事件、经验类型与来源，跨会话召回、纠错、忘记和恢复策略。
3. **经验到技能**：统一学习调度、候选版本、回归用例、自动激活/回滚、可见进化记录。
4. **脚本与高级进化**：隔离 runner、脚本验证、能力范围、任务重放，选择是否接入离线 Harness²。

记忆验收包括：别名/同义表达、时间指代、相似事件区分、用户纠正、短期指令不覆盖长期偏好、旧事冷检索、遗忘后不再生成、来源不存在时不编造。初始准备约 20 个脱敏用例并分开发现问题用例和保留回归用例，避免只在被反复调参的样例上看效果。

自进化验收包括：失败经验可复用、成功方法沉淀、错误候选不替换原版、脚本可终止、回放不重复投递、版本可回退、用户技能不被覆盖、同一反馈不重复学习、暂停/重启后队列状态一致。记录质量、额外模型调用/费用、延迟和峰值 RSS。

RBAC验收包括：角色授权、单独授权及既有优先级一致；微信与Web权限一致；越权访问会话/记忆/技能/报告被拒绝；删除模块无悬空权限；后台进化和定时任务不可绕过授权。Token统计验收包括：与已知调用用量核对、去重、真实重试计量、后台任务归属、日期边界、排行排序与Trace清理后汇总保留。邮件/PDF验收包括：未启用时普通聊天正常、按需生成与发送、历史任务兼容、失败只重试投递、附件权限与资源上限。

助手主体继续以单 worker、受控 Agent 缓存和有界队列部署。训练/验证若需要额外资源，可以用远程模型与 runner，不能以“主体内存低”掩盖额外进程占用。
