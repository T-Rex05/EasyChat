# EasyChat 权限专项核查与整改方案

日期为 2026-11-09。本轮仅核查和制定方案，未修改权限定义、角色授权、前端权限行为或运行配置。

## 1. 范围和依据

核查涵盖 access 注册表与种子同步、角色和用户覆盖、资源归属、各业务模块公开 service 与 HTTP 入口、Web 路由/菜单/角色表单、微信命令、业务工具和 Hermes 工具组。

对当前 easychat-v2 的 app.db 使用 SQLite mode=ro 和 query_only 读取权限元数据及角色授权汇总，未读取用户业务内容、密码或凭证。结论对应核查时点的源码与运行库。

本次采用静态路径核查和只读元数据比对。没有重跑带角色变更的测试，也没有在真实库中增删权限。下文的权限矩阵与拒绝场景属于后续整改验收要求。

## 2. 结论

### 当前运行库

| 项目 | 核查结果 |
|---|---|
| 源码注册权限 | 24 个 |
| 数据库 permission_defs | 24 个，与源码一致 |
| 废弃权限定义 | 当前运行库未发现 |
| 废弃角色授权、用户覆盖 | 当前运行库未发现 |
| admin 已存授权 | 21 个，比当前默认模板少 3 个超级代理权限 |
| user 已存授权 | 13 个，比当前默认模板少 2 个超级代理权限 |
| super_admin 已存授权 | 0 个，运行时按注册全集计算，这个数值不表示没有权限 |
| admin 工具组 | 当前存有 terminal/file/web/notification/schedule，共 5 个 |
| 当前新建 admin 工具组模板 | web/notification/schedule，共 3 个 |

管理员缺少 `superagent.view/create/manage`，普通用户缺少 `superagent.view/create`。这是“已有授权角色不补种”的行为，不能直接判定为用户应当获得但漏授的权限。应呈现权限升级差异，由拥有者明确决定。

当前存在的主要问题包括权限显示过细、定义与实际语义不一致、同功能各入口覆盖不一致，以及历史角色和当前模板的差异不可见。

## 3. 为什么“其他”包含 13 项

角色表单只显式分组 chat/trace/schedule、skill/memory、system，其余均进入兜底分组。

“其他”的组成恰好是

- evolution 2 项。
- file 3 项。
- ledger 5 项。
- superagent 3 项。

这些大部分具有真实功能。应按产品功能归组，并增加模块级配置入口。单纯删掉复选框会掩盖底层授权，单纯增加更多分组则仍会留下操作负担。

依据为 `agent_frontend/src/views/admin/RoleEditDialog.vue` 的 PERM_SECTION_RULES 和 groupedTree。

## 4. 全部 24 个权限的处置建议

| 当前键 | 实际覆盖或问题 | 整改建议 |
|---|---|---|
| chat.use | 发起对话、微信入站、收藏收件、部分学习触发 | 主界面归为“智能对话”，展示包含的基础能力 |
| skill.create | 本人技能创建、修改、版本激活等，名称偏窄 | 模块级显示“使用个人技能”，细项置于高级设置 |
| skill.manage | 跨用户管理，同时可操作本人技能 | 归为技能模块的数据范围及管理能力，菜单允许 manage 用户进入 |
| memory.view | 本人记忆列表/召回及情绪读取，有实际调用 | 改名“读取与召回记忆”，消除“监控”旧命名 |
| memory.edit | 记忆写入/修订/遗忘，情绪启用/记录等 | 模块级显示“记忆与情绪”，写操作口径统一，保留个人关闭采样的独立入口 |
| terminal.audit | 仍注册和默认授予 admin，当前维护业务未找到消费入口 | 进入退役清单，确认新审计产品范围后再决定绑定新实现或删除 |
| cron.create | 仅创建时检查，已有提醒的查询/启停/删除主要按本人归属 | 显示“提醒与简报”，明确禁用模块对已有计划的影响 |
| system.manage | 用户/角色/覆盖授权/渠道绑定及多模块跨用户操作 | 拆清身份管理与业务数据范围，权限页保留一个身份管理入口，高风险授权单独说明 |
| system.config | 模型与 SMTP 等系统配置 | 保留独立“系统配置”，标明凭证与平台范围 |
| trace.view | 排行要求它，本人明细部分入口只校验身份 | 改为“查看用量”，统一页面和 API 入口规则 |
| trace.manage | 允许跨用户明细及清理调用记录 | 改名“管理全局用量”，明确包含清理操作，不能继续仅标“查看全部用户” |
| evolution.view | 本人经验列表，前端独立入口不足 | 收进技能高级设置或经验子页，先明确用户可见交付 |
| evolution.manage | 已注册，但进化暂停使用 system.manage，回滚使用技能权限 | 统一进化治理策略后合并/退役，避免保留没有接线的开关 |
| file.upload | files 实际上传校验，聊天和账单均依赖 | 作为模块依赖能力，普通配置界面收起 |
| file.read | 下载/读取/提取引用校验，多模块依赖 | 同上，保留 owner 和引用范围规则 |
| file.delete | 删除原件或引用的不同范围 | 高级设置保留删除策略，模块禁用时仍可按明确个人数据清理规则处理 |
| ledger.view | 本人账本、导入、统计与候选读取 | 合并展示到账单模块，支持只读模式 |
| ledger.import | 导入、解析、候选与提交，常依赖 file 权限 | 模块级“使用账单”自动展示依赖，避免选中后实际无法上传 |
| ledger.edit | 分类/备注、退款关联等写操作 | 普通“可使用”模式涵盖，高级只读模式可以关闭 |
| ledger.export | 报告生成，下载依赖 file.read | 同模块展示，明确报告生成与读取链路 |
| ledger.manage | 创建本人账户、分类等，描述却称跨用户管理 | 修正描述和调用边界，当前常见 owner 查询仍严格按本人，不能据此宣称已支持跨用户账本管理 |
| superagent.view | 本人任务和轨迹读取，跨用户还需 manage | 编码模块的只读模式 |
| superagent.create | 创建、本人取消/重试，worker 执行/发布重检 | 编码模块的可执行模式，明确会消耗模型并产生远端代码产物 |
| superagent.manage | 仓库/凭证/策略配置及跨用户任务管理 | 保留在管理能力中，不随普通编码使用自动开启 |

上述“合并展示”先通过统一 capability 解析保留原子授权。待旧角色的实际使用和迁移结果明确后，再减少持久化键数量。

## 5. 功能覆盖的具体不一致

### 5.1 菜单与 API

- 技能入口只检查 skill.create，后端允许 skill.manage 操作技能。仅持有 manage 的自定义角色可调用服务，却可能进不了页面。
- 记忆菜单只检查 memory.edit，列表和召回检查 memory.view。只读角色缺入口，仅有 edit 的角色进入后又可能加载失败。
- 用量菜单允许 trace.view 或 trace.manage，排行 API 要 trace.view，本人明细按本人规则允许读取。应将入口与子能力明确对齐。
- 超级代理管理入口先受到 superagent.view 路由限制，单授 manage 不代表能使用全部页面流程。角色编辑应呈现依赖。
- 微信偏好页面使用 chat.use，偏好更新只要求可信身份，情绪读取使用 memory.view，微信命令启用情绪调用 memory.edit。当前一个页面包含多个不同授权口径，缺少按实际 capability 的局部展示。
- 账单页面以 ledger.view 入场后展示上传、修改、导出等操作，后台逐项拒绝。只读模式应直接呈现可用操作和权限说明。

这些现象中的部分是授权层次差异。整改应先定义期望，再统一前端和后端实现。

### 5.2 角色保存与升级

`AccessRepository.seed_builtin_roles` 在角色授权数为零时写入默认授权。这会同时造成两个问题。

1. 已有角色有任何授权时，新增默认权限不会补入。
2. 管理员明确保存空权限的内置 admin/user，后续启动会再次补入默认授权。

第二项应优先修复。角色是否初始化必须用单独版本/初始化记录表达，不能使用授权数量判定。

`upsert_permission_defs` 只新增或更新注册定义，`list_permission_defs` 返回数据库全部定义。当前库恰好没有遗留定义，但未来删除源码注册项时，这两处无法自动把该项从界面安全退役。

### 5.3 授权覆盖与工具

- 用户覆盖规则为撤销优先于角色/单独授予，super_admin 运行时取全集。旧键在普通角色有效权限计算中未统一过滤为注册全集，退役时需要同步处理读取和历史记录。
- system.manage 包含分配角色和授权的能力，当前也允许分配超级管理员角色。应明确只有系统拥有者可管理拥有者身份，以及管理员能委派的权限上限。
- 前端用户管理与角色编辑未解释用户级 grant/revoke。角色勾选后某个用户仍被单独撤销时，会产生“保存不生效”的观感。需要有效权限预览，显示来源与撤销原因。
- 角色创建校验 toolsets，角色更新路径主要检查 permissions，未同步执行同等工具组合法性校验。运行时虽会过滤未知工具组，数据库和界面仍可能出现不可执行配置。
- 角色编辑的工具组离线兜底仍含已废弃的 data/知识库检索。接口失败时会重新显示旧项，应由统一注册元数据生成，或明确停用编辑。
- 业务提醒、账单、收藏和编码工具注册为 __always_available__，由 service 权限控制。因此“定时任务”工具组复选框并不能完整控制新业务提醒工具。必须梳理实际调用链，避免两个开关表达同一个功能却互不对应。
- 当前 admin 保存了 terminal/file，当前新建 admin 模板没有这两项。迁移时需要显示差异和风险等级，保留明确决策与审计。

## 6. 推荐的角色编辑界面

### 普通配置只展示 9 个功能项

| 功能项 | 用户可理解的配置 | 底层对应 |
|---|---|---|
| 智能对话 | 关闭 / 使用 | chat.use，以及收藏、基础偏好等已定义范围 |
| 记忆与情绪 | 关闭 / 只读 / 使用 | memory.view/edit，情绪记录继续要求本人 opt-in |
| 个人技能 | 关闭 / 只读 / 使用 | 技能读取、skill.create，进化子能力单独展开 |
| 提醒与简报 | 关闭 / 使用 | cron.create 与实际任务治理规则 |
| 账单 | 关闭 / 只读 / 使用 | ledger.view/import/edit/export 与受控文件依赖 |
| 编码代理 | 关闭 / 只读 / 执行 | superagent.view/create，仓库仍由配置绑定 |
| 用量统计 | 关闭 / 查看 | trace.view，与本人/全局范围分开 |
| 用户与角色管理 | 关闭 / 管理 | 身份管理 capability，委派边界受系统拥有者约束 |
| 系统配置 | 关闭 / 配置 | system.config，敏感凭证操作按配置入口约束 |

“个人技能只读”目前没有单独原子键，应通过统一 capability 明确定义，不能随意把 skill.create 当成只读授权。

每行先使用整体开关，只在有实际只读需求时展开模式。功能说明展示“包含哪些操作”和“依赖哪些能力”。新增功能没有登记到界面元数据时，构建检查失败，避免再次全部落入“其他”。

### 高级设置

保留三个清楚区块。

1. 数据范围，按技能、用量、编码任务等选择本人或经授权的全局。账本全局管理需先实现真实 owner 语义，再提供选择。
2. Agent 能力，联网搜索、受控代码执行等。terminal/file 结合执行环境和策略治理，高风险操作单独启用。实际角色工具组、可见工具 schema 和 service 权限共同生成有效能力。
3. 高级原子授权与兼容配置，为旧自定义角色保留精确状态、依赖缺失和用户覆盖，普通用户默认收起。

旧角色出现部分原子授权时显示“自定义/部分授权”，不得自动扩成完整功能授权。

super_admin 显示“系统拥有者，拥有全部已启用权限”，业务权限区只读。角色权限数量与其实际能力采用一致展示。普通 admin 的委派范围和跨用户能力仍需显式确认。

### 与另一种方案的取舍

也可以立即把 24 个数据库键替换成 9 个模块键。迁移会失去旧角色的只读、导出、跨用户等差异，容易改变授权范围。

推荐先完成“9 个前台功能项 + 统一 capability + 高级兼容”，待迁移验证完成再退役冗余键。这一轮即可显著减少操作量。

## 7. 统一的权限来源

建议在 access 内增加唯一权限目录，原子定义、功能分组、操作、依赖、数据范围、风险等级、默认模板、生命周期统一存储或生成。

新增窄接口的建议语义

```text
capabilities(principal) → 当前用户功能、操作、数据范围、工具能力、不可用原因
authorize(principal, operation, resource_owner, context) → 允许或明确拒绝
role_preview(role_id, proposed_config) → 变更前后有效权限、依赖、升级/降级差异
permission_upgrade_preview() → 新增、退役、替换和模板版本差异
```

可信用户身份仍由 Principal/ToolContext 提供。Web、微信命令、模型工具、worker 和发布动作经过同一公开 service 授权。菜单和按钮消费 capability 输出。业务资源仍必须检查 owner，隐藏菜单不会替代 API 校验。

权限撤销后停止新的副作用动作，队列和发布边界复查。本人关闭情绪采样、退订主动消息、停止已有任务等操作需要明确的撤销/退出通道，避免功能关闭后反而无法停止已有自动行为。

## 8. 实施顺序

### P0 固定语义和可验证基线

- 建立全部 HTTP 路由、微信命令、业务工具和 worker 操作的操作目录。
- 每项记录当前所需权限、资源范围、依赖、异常语义和前端入口。
- 确认 9 个模块的最终名称，以及系统拥有者/管理员/普通用户的默认差异。
- 导出当前角色与用户覆盖的只读授权快照。当前缺失的超级代理权限列入待决清单。

交付为操作矩阵、角色矩阵、退役清单与升级预览，先不改授权。

### P1 修复授权一致性

- 为内置角色增加初始化/模板版本记录，修复显式清空后重启又恢复权限。
- 权限目录增加 active/deprecated/retired 生命周期。旧记录保留审计，退休键不参与有效授权。
- 校验创建和更新角色的权限及工具组。明确角色委派上限、自身降权和最后一个拥有者保护。
- 统一技能、记忆、用量、偏好、提醒、账单和编码模块的服务检查与页面 capability。
- 暂停展示 terminal.audit/evolution.manage 的可编辑承诺，按最终实现决定退役或正式接线。

主要文件包括 access 的 contracts/policy/api/repository/routes、新增数据库迁移、各模块 api，以及 runtime/tools 的实际能力映射。

### P2 精简前端

- RoleEditDialog 改为 9 个模块项与高级设置，移除兜底“其他”。
- router、AppSidebar、页面操作按钮统一读取当前用户 capability。
- UserListPanel 增加用户有效权限预览，显示角色、单独授予和单独撤销的来源。
- 模块部分授权保持可见，依赖项采用明确提示和变更预览。
- 元数据覆盖检查确保每个 active permission/operation 都有准确分组。

### P3 受控迁移

- 已有角色首次读取旧原子配置并生成兼容 capability，保留权限范围。
- 新角色使用新模板。已有角色模板升级先展示差异，特别标注编码执行、跨用户、代码工具和凭证操作。
- 使用迁移版本和显式用户选择区分“尚未初始化”“明确空授权”“拒绝新增权限”。
- 采用双读/兼容期，再逐步退役旧别名。旧键和新模块之间的每条映射都要有覆盖和拒绝测试。
- 回滚前保留角色、用户覆盖和模板版本快照，防止旧版本播种逻辑再次补权。

## 9. 必须通过的验收

1. 数据库与源码目录差异可见，废弃项不重新出现在角色表单。
2. 内置角色保存空权限，重启后仍为空。
3. 已有角色未确认升级时，新增编码或全局权限不会被自动授予。
4. 仅有技能管理权限可以到达相应管理入口，记忆只读角色可以读取且不能修改。
5. 普通模块开关、API、微信命令和模型工具结果一致。后台 job、执行和发布复查当前授权。
6. 账单上传、导入、报告和下载的依赖完整，关闭某模块不会开放无关文件删除或全局读取。
7. 关闭工具组和关闭业务功能有清晰且一致的实际效果。
8. 用户覆盖的撤销优先规则可解释，退役键不会留在有效权限中。
9. super_admin 的真实权限与展示一致，拥有者身份与委派操作有保护。
10. 本人可关闭采样、退订和停止自动任务，数据范围始终按可信 owner 校验。
11. 所有 active 注册项均有 UI 分组或明确 internal 标识，所有用户可触发操作都有授权策略。
12. 不修改授权的页面操作不会触发默认模板重新播种。

## 10. 建议先确认的产品决策

建议采用 9 个模块项，默认收起原子授权。普通用户的编码能力由系统拥有者明确分配，已有角色保持当前范围直至确认升级。进化能力并入技能高级设置，操作审计在有完整可交付界面和服务校验后再作为功能开放。

这些是整改建议，当前尚未实施。尤其当前 admin 的 5 个工具组、缺失的超级代理授权以及用户覆盖均保持核查时的实际状态。
